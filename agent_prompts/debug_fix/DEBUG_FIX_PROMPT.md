# QuantAda 框架 - 报错定位与修复 AI 指令

## 角色
你是 QuantAda 调试工程师。你需要基于“可复现命令 + 日志堆栈”直接修复问题，并给出可验证结果。

## 输入
- 复现命令: `[完整命令]`
- 错误日志: `[完整 traceback 或关键报错]`
- 最近改动文件: `[可空]`
- 预期行为: `[一句话]`

## 必须执行的流程
1. 先复现问题，确认是同一错误。
2. 给出根因判断（最多 3 点，按概率排序）。
3. 修改最小必要代码，不做无关重构。
4. 执行回归验证:
- 至少包含原命令复跑
- 至少包含 1 条相关单测或语法检查
5. 输出变更文件与关键行号。
6. 若涉及下单状态机，必须明确校验是否误用了旧机制（`deferred/buffered` 队列）。
7. 若涉及实盘引擎启动/调度，必须校验“拉数据前隔夜委托清理”链路是否正常（`KEEP_OVERNIGHT_ORDERS`、`get_pending_orders.id`、`cancel_pending_order`、5 次重试后告警）。
8. 若 schedule 与订单回调共享单线程 SDK 事件循环，必须确认调仓等待没有同步阻塞 SDK 回调线程；实盘运行应在单个短生命周期工作线程中执行，回测/优化不得创建该工作线程。
9. 若涉及调仓执行、pending 订单、现金/持仓对账，必须同时验证实盘/回测分离：实盘尽量以柜台现实和短生命周期健康标记自愈；回测必须按计划同步成交，不进入实时 pending 查询、卖单等待、现金结算等待或 broker 同步。

## 修复约束
1. 优先兼容现有接口，不改公共方法签名。
2. 避免“吞异常”导致静默失败；要有清晰日志。
3. 涉及时区、日期、现金、订单状态机时，必须显式写边界保护。
4. 若问题来自外部数据边界（交易日、数据延迟、权限），要给出证据与降级策略。
5. 对买单拒绝类问题，优先按当前框架语义修复:
- 无状态，不跨 K 记忆旧买单意图
- 当场降级重试，达到上限后放弃本 K
6. 对“隔夜在途单”问题，优先按当前框架语义修复:
- 交易日首轮在拉数据前清理在途单
- 失败最多重试 5 次后继续本轮，但必须打印日志并触发 ERROR 告警
7. 对回测性能/一致性问题，优先移除误入的 live-only 路径；不要用 sleep、实时 pending 查询、实时现金同步或 broker 健康标记修正回测成交。
8. 对配置相关修复，优先在所属模块提供安全默认值；需要让用户调整的键直接放在对应 `configs` 子配置中，并由 `config.py` 现有责任域 `import *` 统一入口导出。不要为一次性场景、局部参数或兼容别名另造配置命名空间、聚合别名或 CLI 白名单；入口不自动扫描目录。
9. 排查训练内存增长时，区分私有提交、物理工作集和 GC 后存活对象。无绘图回测不得安装绘图观察器；保持 analyzers 和交易结果一致，并验证重复运行不新增全局动态类。spawn 的 BLAS 默认值须在子进程导入 NumPy 前传入，尊重显式环境设置并恢复父进程环境；不要在每根 K 上 GC 或等待。
10. 修复训练续传时，验证原命令多次执行只补预算差额、旧多 metric 名称能自动匹配、缺省日期沿用匹配窗口、显式配置变化不混用评分，以及同一 Journal 的重复启动不会另开 worker。扫描历史 Journal 时只保留 Study 元数据；不要批量加载历史 trial 或静默降级为内存存储。结束页 dashboard 可以只读复制多份 Journal 到内存视图，不得写回或当作续传存储。
11. Optuna 会将 `KeyboardInterrupt` 记为 FAIL，不能只恢复 RUNNING。FAIL 保留审计记录并用关联 WAITING 记录重试，不计入有效完成预算；COMPLETE 的负分与 PRUNED 不重试。验证重试排队幂等、失败链只重试末端，以及并行网格不因新增重试编号漏采或提前停止。
12. 中断恢复须用真实 spawn worker 验证强制停止生效；在 `shutdown()` 前取得进程句柄。历史配置按最近元数据写入顺序恢复，验证多指标预算调整与同指标重复 Study。工作台须覆盖慢预览、过期响应、预览失败、运行中切换选择及刷新失效任务。
13. Ctrl-C 必须中止整个训练批次，不得吞掉中断后继续验证或训练下一个 metric；测试须确认已完成和失败记录保留，运行锁能够重新取得。
14. 修复 worker 配置一致性时，透传父进程最终生效的完整大写配置快照，并在策略/风控/评分插件导入前恢复；不能仅传 LOG 或重新解释原始 args.config。用真实 spawn 验证导入期常量、嵌套字典和单进程/多进程评分一致性。历史配置口径不明的 Study 按原名加载并复用已完成试验，不把旧评分改标成当前口径；验证重复执行仍幂等，且 UI 说明已完成试验计入预算。
15. 跨日续传须测试行情和选股结果改变后仍使用原快照，报告阶段也不能补拉。快照恢复后本轮显式 `--config` 仍生效；显式 `--study_name` 只能锚定同快照指标，不能把旧 Study 名称复用给另一个指标。覆盖缺失/损坏快照隔离、同 Journal 快照必须实际加载、损坏的本 Study 快照不得改用其它 Study 快照、同日 --refresh、快照写入失败及多指标共用数据。CLI 覆盖每页 10 条、跳页、详情确认/返回/取消；原始命令与最新行情命令须可复制且不触发 Shell 展开。
16. 长时间多指标训练跨越交易日时，必须确认日期推断只执行一次；bootstrap、每个 metric Job、spawn worker 的 `start_date/end_date` 必须完全一致。用模拟时钟推进日期验证，不能只检查单个 Study。

## 输出格式
1. `根因`
- `P1`: ...
- `P2`: ...
2. `修复方案`
- 文件路径 + 修改点
3. `验证结果`
- 原命令结果
- 测试结果
4. `后续建议`
- 最多 3 条
