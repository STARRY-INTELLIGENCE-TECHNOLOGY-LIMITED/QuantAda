# 优化器运行期

本文件约束参数优化器的日志、进程、数据窗口与 Study 续传行为。

## 1. 终端输出日志
1. 优化模式启动后，框架必须将当前进程的 stdout/stderr tee 到终端日志文件。
2. 终端必须继续滚动输出；文件写入必须走后台队列，避免磁盘 IO 阻塞训练主路径。
3. 终端日志目录为 `.data/optimizer`。
4. `.data/optuna` 仅用于 Optuna journal/dashboard 数据，不承担终端输出归档职责。
5. 如果后台队列满，允许丢弃日志片段并在日志文件中记录丢弃计数；不允许因此阻塞 trial 计算。
6. Optuna 的 Trial 完成、剪枝和失败日志在同一行改写，不另起一行。编号改为 `Trial {编号}/{目标预算}`，剩余时间紧跟编号，避免被参数字典挤到行尾。分母是当前指标的目标预算（含网格上限），不是单个 worker 配额，也不是续传剩余额度。`Best is trial` 保持原样。
7. 剩余时间按本次运行的墙钟速度估计。COMPLETE 与 PRUNED 计入速度，FAIL 不计入；续传开始前已完成的数量从目标中扣除，但不计入本次速度。多进程共用父进程起点和一个共享计数。不足 1 秒或尚无计入完成时显示 `ETA unavailable`，剩余为 0 时显示 `finishing`，其余显示 `ETA 6h12m` 这种英文时长。不修改 Journal trial_id，不新增配置开关。
8. 后台 Dashboard 不得改动进程级 optuna logger 级别。只过滤 Dashboard 线程自身的 Optuna 日志；训练线程的 Trial 完成、剪枝和失败日志必须继续输出，并仍按第 6 条在同一行改写。重复启动不得叠加过滤器，Dashboard 退出后必须卸下该过滤。

## 2. 提权重启
1. Windows 自动提权重启必须保留控制台窗口，避免训练结束或异常时窗口直接消失。
2. 自动提权时必须通过 `QUANTADA_OPTIMIZER_TERMINAL_LOG` 环境变量透传同一个日志路径，让提权前后的输出写入同一份日志。
3. 终端日志没有命令行参数入口；用户命令不应包含内部日志路径参数。
4. 终端日志文件名应复用 Optuna study 的日期/周期/metric/市场命名风格，并写入 `.data/optimizer`。
5. Windows 提权命令必须在执行 Python 前显式切回仓库工作目录，不能把 `.data/optuna` 或 `.data/optimizer` 写到 `C:\Windows\System32`。
6. Windows 提权重启必须把当前进程环境变量写入新的管理员 PowerShell；`ShellExecute runas` 不会继承当前会话的 `$env:`。转发后必须再覆盖 `QUANTADA_DISABLE_AUTO_ELEVATE=1`，避免递归提权。Unix 继续使用 `sudo -E`。

## 3. 工作进程
1. 多进程 worker 应追加写入同一份终端日志文件。
2. worker 的日志 tee 同样必须异步，不能引入跨进程锁等待作为训练主路径依赖。
3. worker 遇到内存压力时应停止本轮 worker 并保留已写入 JournalStorage 的 completed trials；父进程可用已完成结果继续生成报告，不应把已有训练成果丢弃。
4. worker 因内存压力导致进程池破裂或异常退出时，父进程应停止当前 metric 的剩余 worker，并继续使用 JournalStorage 中已完成的 trials；不应把该 metric 直接判为致命崩溃。
5. TPE `n_ei_candidates` 应保守动态调整：普通训练与共享内存可用的多进程训练保持 Optuna 默认候选数；仅在长跑 trial 规模且 spawn 数据共享不可用、需要回退 payload copy 时，按 trial 规模做对数降档以降低内存峰值。
6. spawn worker 在未显式设置 `OPENBLAS_NUM_THREADS` 时默认使用 1，必须在启动子进程、导入 NumPy 前生效；全部任务提交后及启动失败时恢复父进程环境。用户显式设置的标准环境变量保持原值，单进程训练和 fork 已加载库的线程设置不在此边界修改。
7. 创建训练进程池前须回收前置验证回测的循环引用；每个 trial 继续使用 `gc_after_trial=True`。优化器不得在导入阶段加载未使用的可视化模块。
8. `enable_plot=False` 的回测/优化不安装默认或自定义绘图观察器，避免 Backtrader 多标的 `DataTrades` 动态类跨 trial 累积；评分和报告需要的 analyzers、交易与历史行情语义保持一致，启用绘图的回测保留对应观察器。
9. 强制停止进程池须在 `shutdown()` 清空进程表前保留 worker 句柄，终止后进行有界 join；超时再 kill 并等待回收，避免退出后 worker 继续写 Journal 或持有共享行情。
10. Ctrl-C 中断整个训练批次，保留已持久化试验并释放运行锁，不再启动验证回测或后续 metric；下次续传按失败/中断恢复规则处理。
11. 进程 payload 必须深拷贝父进程 `config.py` 入口中所有已生效的大写配置值，包含 CLI 覆盖、聚合字典和运行期日志开关。worker 在加载策略、风控、评分插件前应用完整快照；不重新解析原始 `args.config`，不另建配置白名单或仅传 LOG 的旁路。缺失快照时在打开 Journal 前明确失败。

## 4. 验证报告
1. 优化器最终摘要应同时输出训练后主回测（MainEval）、测试集回测和年度固定窗口回测，方便人工或 AI 直接分析参数稳定性。
2. MainEval 回测窗口必须至少覆盖最近 3 年；如果训练+测试逻辑窗口更长，则覆盖完整训练+测试逻辑窗口。该窗口不包含 warm-up 起点，warm-up 只用于指标计算。
3. MainEval 回测必须优先复用优化器已加载的 `raw_datas` 切片；切片前须把 tz-aware 索引转到 naive UTC，避免与窗口边界比较失败后误去补拉。只有本轮初始请求窗口确实未覆盖目标窗口时，才允许按缺口向数据提供者补拉。窗口对齐周期性打印 reuse/fetch 进度；期权末根早于窗口结束时不逐合约刷屏。
4. 年度固定窗口回测必须复用优化器已加载的 `raw_datas` 切片，不得额外调用数据提供者补拉数据，避免浪费外部行情配额。
5. MainEval 和年度固定窗口都是训练后报告，不参与 trial 目标函数评分，避免显著拖慢机器学习主路径。
6. 期权策略评分可使用期权专用 metric；优化器应向评分函数提供 Short Put/PCS 的风险资本、权利金、MAE、最差交易和尾部损失汇总，不得只用账户级收益率替代担保资金收益率。
7. 有限离散参数空间必须使用去重网格采样；`n_trials` 不得通过并行 TPE 重复执行相同参数组合。连续参数空间仍可使用 TPE。失败或中断试验的恢复按第 6 节处理，不重复已完成组合。
8. 同一 worker 的期权 trial 可复用首次构建的对齐行情；期权的对齐行情与离线可见行缓存必须按完整时钟签名和精确当前时间隔离，实盘不得启用这些缓存路径。股票优化保持原有 trial 数据对象路径，不复用期权式对齐结果。
9. 优化器默认按训练配置自动匹配已有 Journal/Study，兼容旧的带运行时间名称；没有匹配时使用配置与窗口摘要生成稳定名称。多 metric 各自恢复真实名称。缺少的 metric 使用只含该 Study 的 Journal，避免 trial_id 与控制台编号岔开；批次用 `_optimizer_batch_journal` 关联。不得给已存在的名称再追加后缀。显式 `study_name` 和 Journal 路径仍可用于指定任务。
10. 训练 Journal 仍按 Study 拆分，不合并文件。多 metric 训练结束时，dashboard 把各 Journal 复制到只读内存视图后同时展示全部 Study；打不开的文件跳过，全部失败才退回最后一份。单份 Journal 直接打开。该视图不写回训练 Journal，笔记不会进入原文件。

## 5. 启动调度
1. `--opt_schedule` 只负责优化/训练进程进入优化器前的启动等待，不改变 trial、worker 或回测的同步执行语义。
2. 支持 `HH:MM[:SS]` 单次本机时间触发，以及 `Nd|Nw|Nm|Nh[:HH:MM[:SS]]` 周期触发；`N` 为正整数，`Nw` 以本机周一为锚点。
3. `HH:MM[:SS]` 等待当天或次日该时刻，然后才自动推断 start/end；周期规则等待下一次槽位。等待使用阻塞睡眠，不要忙等占用 CPU。实盘 schedule 不接受一次性 HH:MM。

## 6. 自动续传与重复执行
1. 匹配依据包括策略、选股器或有序标的列表、数据源、固定参数、搜索空间、风险控制及参数、现金、佣金、滑点、K 线周期、训练/测试切分和完整显式配置覆盖。字典格式和键顺序不影响匹配；并行度、trial 总预算、metric 顺序和顶层展示参数不参与训练身份。
2. 自动发现从 `.data/optuna/optuna_*.log` 中优先选择最近更新的匹配批次；按 Study 元数据匹配，不从文件名猜测实际 Study 名称。只扫描 Study 元数据；同一文件有多份匹配 Study 时用现有轻量计数比较完成数，不把历史 trial 重放成内存对象。旧记录缺少必要元数据时不自动复用。
3. 未显式指定日期且命中已有任务时，沿用其原始窗口，跨天重跑也不漂移。开始新窗口应显式指定 `--end_date`；非滚动模式还比较 `--start_date`。滚动窗口由结束日期和训练/测试周期决定。`--opt_schedule` 等待结束后按当前槽位推断窗口，不冻结到旧槽位。
   一次命令请求的多指标/多组训练只在批次入口推断一次 `start_date/end_date`；所有 bootstrap、metric Job 和 worker 必须使用同一窗口。批次运行跨越多个交易日时，不得按每组开始时间重新推断。
4. 同一批次内逐 metric 匹配；COMPLETE 和主动 PRUNED 计入总预算，FAIL 不占有效完成额度；正常完成的负分也是有效结果，不重试。达到预算的指标不再执行目标函数，未达到时只补差额。取得命令运行锁并排除旧任务仍在运行后，将遗留 RUNNING 恢复为 Optuna WAITING，保留原编号、网格身份和已采样参数。FAIL 是不可修改的终态，保留原记录，使用 Optuna `failed_trial` / `retry_history` 血缘创建 WAITING 重试记录，保留参数、分布和网格身份；已有后续尝试的失败记录不得重复排队，只处理重试链末端。每次启动只登记一次待重试快照，重试再次失败时留待下次续传，不在本轮无限重放。
   重试记录不消耗新网格槽位；旧 FAIL 占满网格时不得提前停止尚未执行的重试。基准与验证报告仍按现有流程生成；单次被中断回测从头计算，不保存 K 线执行进度或中间评分。试验总记录数可因保留失败历史而超过 `n_trials`，完成数与预算按有效结束口径统计。
   这些已登记 WAITING 不占用本轮完成差额。剩余完成数大于 0 时，父进程先把它们各执行一次，再用 COMPLETE 与 PRUNED 重算差额，只补未探索组合。成功的重试计入完成数；失败不计入，也不在本轮再次排队。剩余完成数已经为 0 时不执行目标函数，未跑的 WAITING 留待以后提高预算。多进程必须在父进程排空 WAITING 后再拆分新试验，不能让 worker 抢走重试。
5. 同一 Journal 的优化命令使用非阻塞进程锁；重复启动在取数前提示并退出。进程异常退出由操作系统释放锁，不根据锁文件存在与否判定存活。加锁冲突以外的 IO 错误必须抛出，不能当成已有训练而跳过。旧版任务从名称提取启动 PID，新版在 Study 记录当前调度进程身份；Windows 同时检查主进程退出后遗留的 Python worker，并排除已复用的主进程 PID，不自动终止它们。
6. 单 worker 的 CLI 优化也必须使用 Journal 持久化。Journal 追加采用 `JournalFileOpenLock`，不要求单 worker 为创建符号链接提权；Journal 不可用时应明确失败，不能把自动续传静默降级成易失的内存 Study。
7. 显式 `--study_journal` 可单独约束扫描文件；显式 `--study_name` 优先约束任务名称。已有显式名称对应不同 metric、配置或窗口时必须拒绝复用，避免覆盖其元数据后混入不同含义的评分。快照锚点只用于定位同一快照中的其它指标，不得把该 Study 名称分配给未匹配的另一个指标。
8. 自动恢复校验并使用原始数据快照，不重新获取远端修订行情；策略源码版本仍由操作者保证。优化模式的 `--refresh` 表示使用最新行情创建独立实验：不继承旧任务的缺省日期、不读取旧快照、不复用旧评分，原记录保留。同日刷新也必须使用独立 Study；不传刷新时仍按当前任务幂等续传。
9. 完整配置透传仍用内部 `_optimizer_worker_config_version` 标记新 Study。没有该标记的历史 Study 按原名交给 `create_study(..., load_if_exists=True)`，COMPLETE 和 PRUNED 计入预算，只跑未完成组合；不把旧评分改标成当前口径，只记录复用事实。已记录且不等于当前版本的口径仍然隔离。同一批次、同一训练身份和窗口中，同指标选择已完成更多的 Study；误隔离出来的薄 Study 不能盖过已探索更多的原 Study。显式 `--refresh` 仍新建实验。控制台 Trial 编号与该 Study 的 Journal trial_id 一致，从被加载的 Study 继续，不是从 0 开始。

## 7. 交互选择历史训练
1. `python run.py --train_resume` 无需策略位置参数，按 Journal 最近更新时间倒序，每页显示 10 个任务。页底显示总数、当前页和总页数；`n` / `p` 翻页，`g 页码` 跳页，任务使用全局序号。列表中 `q`、`0`、空输入、EOF 或 Ctrl-C 取消；取消不取行情、不启动训练。
   选中任务进入详情页，展示原始启动命令、使用最新行情的手动命令、本次恢复命令与隔离提示。只有 `1` / `y` / `yes` 明确确认才启动；`l` 查看该任务匹配的最新终端日志，不打开另一个窗口或快照的日志，`b` / `n` / 空输入返回当前列表页，`q` / `0` / EOF / Ctrl-C 退出。
   日志默认打开末尾。`n` / `p` 翻页，`h` / `e` / `m` 跳到首页、末尾和中间，`g 页码` 跳页，`s` 跳到展示段开始标记所在页，`b` 返回详情。打开日志只建页起点索引，不把全文放进任务列表。
   列表和详情同时显示训练状态，文案为 `Finished` 或 `Incomplete`。只读取与该任务匹配的终端日志末尾展示段。匹配要求 Journal 文件名一致；日志若写了窗口或快照，也必须与任务一致。同一 Journal 文件对应多个任务、而日志没有窗口和快照时，不得把该日志判给每一个任务。多指标运行把批次 Journal 和各指标专用 Journal 的文件名、窗口、快照 ID 追加到终端日志旁的 `<terminal>.scope`，并在试验开始前打印 `Training scope`；读取时合并头部和该旁路文件，头部在首个 `Starting Optimization` 处停止。不扫描试验全文，不新增持久化任务索引或配置项。展示段规则是：开始标记之后出现结束标记，且结束标记后不是空摘要，才算 `Finished`。空摘要指旧日志中的“训练指标未返回结果”、“所有指标均未返回结果”，新日志中的 `Training metrics returned no results`、`All metrics returned no results`，或同时出现 `Metrics completed: 0` 与 `Completed trials: 0`。空摘要跳过并继续看更早日志；最新真实运行没有结束标记则为 `Incomplete`。优化器只在至少一个指标返回结果后写入这对标记；仅有基准或全部指标失败时不写标记。不扫描试验过程全文，不保存状态，也不因此禁用续传。续传菜单、日志查看和 Trial 进度后缀使用英文，不另做翻译层。
2. CLI 与 command_center 共用 `optimizer.training_tasks` 目录和参数恢复逻辑。任务按 Journal、训练配置和窗口分组。同指标有多份记录时展示各自进度，续传加载已完成更多的那份，不把进度相加。目录缓存只在进程内按路径、修改时间和大小失效，不新增持久化任务索引或配置命名空间。
3. 目录读取只用标准库；计数仅保留每个 trial 的 Study ID 和状态字节，不驻留 FrozenTrial 或参数历史。优化器包的公开运行期 API 按需加载，工作台浏览任务不应导入科学计算依赖。
4. 运行期保存完整请求指标集和实际试验预算。旧任务可从对应终端日志头部恢复尚未创建 Study 的指标；缺少对应日志时仅恢复已有指标，不猜测未知配置。缺少必要元数据或带实盘连接的记录不可交互续传。
5. 选中后恢复保存的策略、参数、搜索空间、风险控制、配置覆盖、日期、指标、预算和并行度，并明确指向选中的 Journal。历史启动调度与强制行情刷新不重放；失败重试和运行互斥继续使用第 6 节的规则。
6. CLI 可显式覆盖已有选项，例如 `--n_jobs`、`--n_trials`；显式配置字典覆盖合并到历史配置。完成选择后重建 argv，并清除会覆盖所选任务的 Study 环境变量，保证提权重启直接执行选中任务，不再次弹出菜单。
7. 同一批次内按 Study 参数快照最近写入顺序匹配和恢复，而非按 Study 创建顺序；多指标中途调整预算或并行度后，交互续传采用最新快照。同指标多份 Study 只展示并续传最新快照对应的那份。
8. 未记录当前配置口径的任务在列表和预览中说明：续传加载原 Study，已完成试验计入预算，只跑未完成组合，控制台 Trial 编号与 Journal trial_id 一致，从原 Study 继续。同一批次另有完成更多的 Study 时，恢复命令指向那份 Study，不把两组进度相加。
9. 保存原始 argv，恢复时回显可复制命令；原始缺省日期保持缺省，不用后来推断的日期冒充用户输入。旧记录只能重建时须明确标注，并保留重建来源标记。最新行情命令移除 Study 绑定和历史调度，加入已有 `--refresh`；显式日期保留，未显式日期在执行时重新推断。Bash/PowerShell 文本必须正确转义，不执行参数中的 `$()`、美元符号或反引号。

## 8. 固定数据快照与跨日恢复
1. CLI 优化在任何基准回测和 trial 前，将本批次的原始行情、实际训练/测试数据、选股结果、展开后的期权合约池、逻辑窗口、预热范围及生效配置保存一次。多个指标、多个 trial 共用同一份快照；不保存 Provider、SDK client、策略实例或指标缓存。恢复快照配置后必须重新应用本轮已解析的显式 `--config`；未覆盖的键保持快照值，不能用当前默认值替换，也不能让快照撤销本轮显式覆盖。
2. 快照位于 Journal 相邻的 `<journal>.snapshots/<id>/`，保存本机数据文件及 JSON 清单。清单记录实际各标的首末时间、索引时区、数据指纹和原始命令；保留行情原有时区，不猜测 naive 索引所属交易所，也不人为补齐休市日。
3. 数据以流式方式写入临时目录，完成并 fsync 后原子提交；清单和数据分别计算 SHA-256。恢复必须先校验清单和数据，再读取本机框架生成的数据文件，不接受任意外部 pickle 路径。
4. 跨日恢复沿用已保存的窗口、标的集合、合约池与数据内容，跳过选股器、DataManager 构造、期权池展开和 Provider 取数。训练、基准、MainEval、年度验证均限于固定数据；缺少某标的或部分尾部行情时不得在报告阶段偷偷补拉。
5. Study 绑定快照引用。已有快照时先校验再复用，不重新取数。本 Study 的快照损坏时重新准备并绑定新快照，不改用同 Journal 其它 Study 的快照；旧评分计入预算，并标记为不是新快照算出的结果。没有快照的旧 Study 不再因缺快照改名：加载原 Study，已完成试验计入预算。同一批次已有快照时必须实际加载并跳过取数，旧评分计入预算但不算该快照的结果；加载失败或没有可沿用快照时重新准备并绑定新快照，不保留损坏引用，也不把旧评分假装成新快照算出的结果。不同快照分别展示，续传选择已完成更多的那组，不把两组评分相加。`--refresh` 仍创建独立实验。数据准备或快照提交失败时明确退出，不退化为各指标分别取数。
   交互恢复当前版本任务时，用已有 `--study_name` 指向选中快照内的一份 Study；匹配同一快照的其它指标，而不是仅按名称前缀查找。不得把用户选择的旧快照自动换成同配置下最新快照。
6. `--refresh` 手动启动与续传使用相同优化引擎，但准备新数据、重新运行选股和期权池展开，并绑定新快照。快照不替代市场交易日历或数据源完整性保证；保存的是本批次实际采用的数据，不宣称数据源提供的最后一根 K 线一定已经收盘。
